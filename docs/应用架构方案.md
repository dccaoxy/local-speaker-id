# 本地录音自动识别：应用架构方案

> 基于现有 `diarize.py` / `winmatch.py` / `identify.py`，把它们包成"目录监听 + 待确认队列 + 确认回灌"的应用。
> 标注 `[MVP]` = 首版必须；`[后置]` = 可以不做。

---

## 1. 进程与 IPC

**一个常驻守护进程 + 一个 UI，不拆微服务。**

```
launchd ──> voiceprintd（Python，单进程，1 个 worker 线程）
              ├─ watcher 线程：fswatch 子进程读事件 → 入队
              ├─ worker 线程：串行跑 convert→diarize→score→render
              └─ HTTP 127.0.0.1:8765（FastAPI + uvicorn）
UI(Tauri/Electron/网页) ──HTTP/SSE──> daemon
```

- 启动方式：`~/Library/LaunchAgents/com.local.voiceprintd.plist`，`RunAtLoad=true`、`KeepAlive=true`、`WorkingDirectory` 指向 venv，日志重定向到 `~/Library/Logs/voiceprintd.log`。用户不用管"开没开"。
- **必须单 worker**：实测 4 线程最快、8 线程反而慢 20%；且一段 60 分钟音频 float32 全量载入约 230MB，两个并发就 OOM。并行只会更慢。
- **用 HTTP 而非文件/信号**：确认操作要双向应答（回灌成功没有、原型重建完没有），要多个客户端（桌面 UI / 手机浏览器 / curl 调试），文件队列只能单向且没有回执。不用 gRPC——单机场景多一层依赖没收益。
- **进度推送用 SSE**（FastAPI `StreamingResponse`）不用 WebSocket：单向、浏览器原生 `EventSource` 自动重连、不用自己写心跳。`[MVP]` 可先用 3 秒轮询 `/recordings`，SSE `[后置]`。
- 队列不放 Redis/Celery：单机单用户，**SQLite 表就是队列**，用 CAS 取任务（见 §2）。

接口（FastAPI 路由）：

```python
GET  /recordings?status=awaiting_review      -> [{id, filename, duration_s, status, clusters: [...]}]
GET  /recordings/{rid}
POST /recordings/{rid}/clusters/{idx}/assign {"name": "张三", "save_to_library": true}
POST /recordings/{rid}/clusters/{idx}/assign {"name": "__unknown__"}   # 明确判为陌生人
POST /recordings/{rid}/finalize              # 需要所有簇都已处置
POST /recordings/{rid}/retry
POST /recordings/{rid}/names {"0":"张三","1":"李四"}   # 手动点名，直通 --names
GET  /events                                 # SSE
GET  /health                                 # 模型是否加载、队列深度
```

## 2. 数据模型

唯一真源：**SQLite `~/.voiceprint/state.db`**（`PRAGMA journal_mode=WAL`）。不要用 json 存状态——json 只能整份原子重写，崩溃时丢全部，UI 轮询要全读。`speakers.json` 降级为**导出产物**（每次回灌后原子写一份，保持老脚本可用）。

```sql
recordings(
  id TEXT PK,            -- sha256(前1MB + 后1MB + size) 内容指纹，不是路径
  path TEXT, filename TEXT, size INTEGER, mtime REAL, inode INTEGER,
  duration_s REAL, status TEXT, n_clusters INTEGER,
  proto_version TEXT,    -- 本次打分用的原型集版本
  error TEXT, attempts INTEGER DEFAULT 0,
  created_at, updated_at, finalized_at
)

clusters(
  id INTEGER PK, recording_id TEXT, idx INTEGER,     -- UNIQUE(recording_id, idx)
  seconds REAL, n_seg INTEGER, sample_text TEXT,     -- 抽 3 句供人眼认人
  assigned_name TEXT,                                 -- NULL=未处置
  match_best TEXT, match_sim REAL, match_second REAL,
  decided_by TEXT,        -- 'auto' | 'manual'
  state TEXT              -- 'auto' | 'confirmed' | 'rejected'
)

jobs(  -- 意图日志，写库先于执行
  id INTEGER PK, recording_id TEXT, stage TEXT,      -- convert|diarize|score|render
  status TEXT,                                        -- queued|running|done|failed
  attempts INT, last_error TEXT, started_at, finished_at,
  UNIQUE(recording_id, stage, status)                 -- 防重复入队
)

speaker_sources(  -- 替代 speakers.json 成为真源
  id INTEGER PK, name TEXT, recording_id TEXT, cluster_idx INTEGER,
  wav_path TEXT, segs_path TEXT, vec_path TEXT,       -- 该来源的窗向量 .npy
  created_at, UNIQUE(recording_id, cluster_idx, name)
)

artifacts(recording_id, kind TEXT, path TEXT)         -- wav16k|segs|report|asr|qvec
events(id, ts, recording_id, level, msg)              -- 给 UI 和排障看
```

三态表达：`recordings.status` 表达"处理中/待确认/已定稿"，`clusters.assigned_name + state` 表达"某簇判给谁、由谁定的"。置信度用 `match_sim` / `match_second` 两个数存原始值（不存布尔），UI 自己决定怎么显示。

## 3. 状态机

```
discovered ──稳定2次──> waiting_stable ──60s无写──> queued
                                                      │ CAS 取任务
                                                      v
                                                 processing
                                            (convert→diarize→score→render)
                                                      │
                                    ┌─────────────────┴──────────┐
                                    v                            v
                        awaiting_review ──全部簇处置──> finalized   failed
                                    │                            │
                            （回灌原型库）                  手动 retry / 3 次自动
```

- **CAS 取任务**：`UPDATE jobs SET status='running' WHERE id=(SELECT ... WHERE status='queued' LIMIT 1) AND status='queued'`，返回行数=1 才执行。多条事件并发安全。
- **崩溃恢复**：进程启动时 `UPDATE jobs SET status='queued' WHERE status='running'`。每个 stage 产物按 `recording_id` 命名、可覆盖，重跑幂等。
- **失败策略**：每个 stage 自动重试 3 次（30s / 2min / 8min 退避）；超限 → `failed` + 通知 + 保留中间产物，UI 给"重试"按钮。`awaiting_review` 不算失败（等人，不超时）。
- **文件在被处理时被改**：render 前重算内容指纹，不一致 → 当前结果标 `superseded`，重新入队一条新记录。

## 4. 文件监听的三个坑

监听用 `fswatch -0 --event Created --event Updated --event Renamed --event MovedTo`（Homebrew，比 watchdog 可靠，能拿到 macOS FSEvents 的原生事件），喂给 Python 的 `subprocess` 逐条读。

**坑 1：半成品文件。** OneDrive 会边写边同步，甚至给你一个 0 字节占位符。
处理：入队前过三道闸——
1. `st_size > 0` 且 `st_blocks > 0`（dataless 占位文件 blocks=0，先 `brctl download <path>` 触发下载再等）；
2. 文件 size + mtime 连续 2 次采样（间隔 `VP_STABLE_SEC=60`）完全不变，且期间没有任何 fswatch 写事件；
3. 转成 16k wav 后读 `sf.info(wav).duration`，与入队时登记时长差 >5% 直接判失败。这是最后一道网——前两道都可能被同步器骗过。

**坑 2：重命名。** 用户会把「录音 1.mp3」改成「面试 张总.mp3」。**身份用内容指纹不用路径**。改名后 fswatch 报 Renamed，用新路径算指纹命中已有记录 → 只 `UPDATE path, filename`，不重跑；已 finalized 的顺带把输出 `.说话人.md` 一起改名（可选）。inode 单独存一份做辅助匹配。

**坑 3：重复事件。** 一次保存通常产生 3–5 个事件。
两层去重：① 内存 debounce，同一 inode 5 秒内合并只留最后一条；② **库层唯一约束**——`jobs` 的 `UNIQUE(recording_id, stage, status)` + 入队前检查 `recordings.status IN ('discovered','failed')`。库层去重才是崩溃后仍正确的，内存态会随重启丢。

## 5. 原型重建的成本与策略

**现状是分钟级，必须改。** `build_protos()` 对每个来源读整段 wav、抽最多 1200 个 2 秒窗、逐窗跑 CAM++（约 20–40ms/窗），单来源约 30–60 秒；而 `register.py` 一注册就 `os.remove(protos.npz)` **全量重算**，10 个来源就是 5–10 分钟。而且全量重建期间界面不能打分。

改成**两级缓存 + 全增量**：

- L1 按来源缓存：`~/.voiceprint/db/emb/<source_key>.npy`，`source_key = sha1(wav_quickhash + cluster + segs_hash + f"{WIN}/{HOP}" + emb_model_mtime)`。命中就 `np.load`，毫秒级。
- L2 原型矩阵：从 L1 `np.concatenate` 得到，纯内存毫秒级。`protos.npz` 不再是真源，只是 L2 的落盘快照。
- `proto_version = sha1(sorted(L1 keys))` 写进 `recordings.proto_version`；版本变了才重算 L2。旧结果 UI 标"由旧原型产生，可重评"。

**回灌零成本的关键**：score 阶段把每个簇的 query 窗向量落盘到 `work/<rid>/q_<cluster>.npy`。用户确认「簇 2 = 张三」时，**直接把这批向量复制成 L1 文件**，不用重新读音频、不用重新推理。整个回灌流程：

```
一个事务：写 speaker_sources → 写 L1 npy → 摘要 speakers.json(tmp+rename)
→ 重算 L2（毫秒）→ clusters.state='confirmed'
→ 触发后台低优先级"仅重打分"任务：对 awaiting_review 的其它录音重跑 score（segs 已有，不重跑 diarize）
```

实测预期 <1 秒，UI 无感。`[后置]` 回溯重评。

顺带两个性能修正：`identify.py` 里每个簇都新建一次 `SpeakerEmbeddingExtractor`（模型重载 N 次），应改为全局共享一个 extractor；`build_protos` 也复用同一个。

## 6. 三个最可能的线上故障

**① 半成品被当完整文件，产出截断稿并"定稿"。**
事后极难发现——报告看着正常，只是少了后 20 分钟。防：§4 三道闸 + 报告页首行强制显示"音频时长 32 分 14 秒 / 12 个簇"，时长是一眼可查的硬指标。

**② 长会议分离塌陷（README 已记录：100 分钟录音 4 个簇里一簇吞 80 分钟）。**
判定全错但界面显示得像正常结果。防：score 后加健康检查——`最大簇时长占比 > 60%` 且总时长 > 40 分钟 → 标 `low_confidence`，UI 顶部黄条"分离可能失败，建议指定人数重跑"，并通知。`[MVP]` 只做提示；分段处理+跨段聚类 `[后置]`。同时把 `--clusters` 的自动值记在报告里，方便复现。

**③ 内存爆炸被 macOS 杀掉 / 重启后任务丢失。**
60 分钟音频 float32 约 230MB，加上 8k 副本和窗切片峰值可到 800MB+。防：单 worker 串行；每段处理完 `del + gc.collect()`；`jobs` 表先写库再执行（意图日志），启动时把 `running` 全部重置为 `queued`，靠产物文件名幂等重跑。launchd `KeepAlive` 兜底重启。`[后置]` 长音频用 `soundfile.blocks` 流式读。

通知：`[MVP]` 用 `osascript -e 'display notification "..." with title "..."'`（零依赖）；`[后置]` 接飞书 connector 推卡片，含"3 个簇待确认"和跳转链接。

# 决议记录 v2（与 pm / ux / ml 对齐后，**覆盖上文 §2、§3、§5**）

## D1. 不装 SQLite：state 分两类，按"能否重建"决定载体

pm 的意见采纳，但前提写死：**可以不装数据库，唯一理由是状态可从磁盘三条来源重建**。

| 载体 | 内容 | 丢了会怎样 |
|---|---|---|
| `~/.voiceprint/state.json` | 上文 `recordings` 表的所有字段 + `stage_ms`。**schema 不变，只换载体** | 丢掉不致命：启动时扫录音目录重建（代价=重跑未定稿的） |
| `~/.voiceprint/decisions.jsonl` | append-only，**不可重建** | 丢=所有人工确认作废。这是唯一真正需要持久化到字节的东西 |
| 内存队列 | `collections.deque` + 单 worker | 丢=重启后重扫，靠 state.json 的 status 跳过已完成 |

`jobs` 表作废，改成内存态 + `state.json` 里每个 recording 的 `stage` 字段。启动恢复逻辑：扫目录 → 对每个音频算内容指纹 → 查 state.json → `finalized` 跳过、`processing` 重置为 `queued`、新文件入队。

**但 state.json / decisions.jsonl 放 `~/.voiceprint/`，不放 OneDrive 录音目录。** OneDrive 会同步它、多端会产生 `state-DESKTOP-XXXX.json` 冲突副本、同步器会锁文件。产物 `.说话人.md` 和预切音频的"给人看的那份"可以落 OneDrive（用户要在同步盘看到结果），但状态文件不行。

## D2. 声纹库要从 OneDrive 搬出来（隐私 + 冲突，双重问题）

现状 `~/OneDrive/数据库/声纹/` 里躺着 `protos.npz` + 3 个人的向量 JSON。两个问题：① 生物识别信息被同步到云端，README 自己写了法律要求；② 多端会互相覆盖 `protos.npz`，而它又是"删了就全量重算"的致命文件。
动作：向量与缓存迁 `~/.voiceprint/db/`，OneDrive 里只留 `使用说明.md` 和纯人名的导出清单（`人物索引.json` 去掉向量字段）。**这条需要用户拍板。**

## D3. 阈值不是"统一成一个数"——是两个不可互换的量纲，但必须单一配置源

技术更正 pm 的判断：`identify.py:28` 的 `0.70` 是 **centroid（整段均值）** 的阈值，`winmatch.py:31` 的 `0.40` 是 **滑窗最近邻中位数** 的阈值。两者不可互换——README/技术结论实测显示：两者同人分数都是 0.487，但异人分数一个是 0.468、一个是 0.376。**同一个阈值放到另一个 scorer 上必然错。**

pm 指出的"默认路径会全判未知"经复核**不成立，这里更正**：`--scorer` 的 argparse 默认值本来就是 `window`（`identify.py:172`），0.70 与 `--threshold` 的默认值只作用于显式指定 `--scorer centroid` 的分支，属于休眠代码，历史产物未受影响。产物头那个 0.45 是手工传参残留，不是配置漂移。

真正的隐患是**三个数并存且没有任何一处能回答"这次判定用的是哪套参数"**，以及一旦有人误用 `--scorer centroid` 却没意识到量纲差异，会得到一整批静默结果。所以仍然收敛到 `config.py`，并且把质心阈值改成 `None` 哨兵——必须显式传参，杜绝"默认值套错量纲"这种错误在无人察觉时发生。

修法：**`src/config.py` 已落地**（本次已建，其他模块改成 `import config` 只读不定义）：
```python
SCORER   = "window"        # 唯一在用的模式
WIN, HOP = 2.0, 1.0
T_AUTO   = 0.44            # ≥ 直接落名字，不打扰用户
T_ASK    = 0.36            # [T_ASK, T_AUTO) 问用户；< T_ASK 判未知
MARGIN   = 0.05
RHO_MIN  = 0.70            # 一致窗占比下限，低于则疑似簇内混人
N_MIN    = 20              # 有效窗数下限
CENTROID_THRESHOLD = None  # 哨兵：质心模式必须显式传参
THREADS  = 4  STABLE_SEC = 60  SEG_MIN_SEC = 1500  SEG_LEN = 360  SEG_HOP = 300
```
`identify.py` 与 `winmatch.py` 已改为 import config（`THRESHOLD`/`MARGIN`/`WIN`/`HOP`/`MIN_DUR` 等旧名保留为别名，调用方零改动），`--threshold` 默认值改为 `None` 并在 `--scorer centroid` 时强制要求显式传入。

## D4. 流水线变 5 段（ml 的分段聚类）

`convert → diarize_seg → merge → score → render`，三段之间**只通过文件 JSON 交接，不共享进程内状态**：
- `work/<rid>/segs_seg.json`：段级簇（每段 6min/步长 5min，含 1min 重叠用于边界去重）
- `work/<rid>/segs.json`：全局簇（cross-segment merge 输出，字段同现在 `{"segments":[{start,end,speaker}]}`，下游完全不用改）
- `work/<rid>/evidence.json`：ClusterEvidence 列表

合并阶段用并查集 + 窗级余弦（300×300 很便宜），**向量按段读缓存不重算**。

⚠️ 这条与 pm 的 P90 指标直接冲突：25 分钟音频预算 150s，分段聚类意味着段内聚类重复开销 + 合并，实测会到 200s+。**P90 ≤ 时长/10 在分段方案下大概率不成立**，要么把指标放宽到 /6，要么按"<25min 单段直跑、≥25min 才分段"做分流。需要 pm 定。

## D5. score 返回契约（ClusterEvidence，取代裸 dict）

```python
@dataclass
class ClusterEvidence:
    cluster_id: int
    duration: float      # D 簇总时长
    share: float         # 占总时长比例
    n_win: int           # N 有效窗数
    s1: float            # top1 中位数得分
    s2: float            # top2 中位数得分
    m: float             # s1 - s2
    rho: float           # 一致窗比例：argmax 指向 top1 且 best>=threshold 的窗数 / N
    top1: str | None
    tier: Literal["很像","有点像","无"]      # 唯一给 UI 的分级，不暴露数字
    reason: list[Literal["too_short","noisy","low_margin","low_rho"]] | None
    longest_span: tuple[float, float]        # 最长段的 [起点, 终点]，UI 直接显示时间戳并定位音频
```
`decide(ev, cfg) -> name|None` 只吃这个结构，分级逻辑不散到 UI。`rho` 在打分循环里顺手统计（矩阵已在手上，零额外推理）。

## D6. decisions.jsonl 契约（ux 的"名字不烧进 md"）

```json
{"v":1,"rec_id":"sha256:...","cluster_id":2,"name":"张彤","action":"assign",
 "one_off":false,"source_id":"src_ab12","proto_version":"p_7f3a","ts":"2026-10-28T11:02:11+08:00"}
```
- **撤销 = 再 append 一条 `"action":"revoke"`**，不删行；当前态 = 按 ts 重放。
- md/segs.json 全部是渲染产物，可随时 `render(rec_id)` 重建，**不重跑分离**。
- 每条 assign 带 `source_id` + `proto_version`，ml 的按来源回滚才有依据：`revoke` 时精确删 `db/emb/<source_id>.npy` 而不是重建全库。

## D7. 预切音频：用 soundfile 不用 ffmpeg，落 Caches 不落 /tmp

```python
def clip(src_wav16k, t0, dur=12.0, out=None):
    with sf.SoundFile(src_wav16k) as f:
        f.seek(int(t0*16000)); data = f.read(int(dur*16000), dtype="float32")
    sf.write(out, data, 16000, subtype="PCM_16")
```
`soundfile` 已在依赖里，定点 seek 只读 12 秒，毫秒级；省掉 ffmpeg 这个 Homebrew 依赖（仓库现在用的是 `afconvert`，它没法按时间裁）。
落盘位置 `~/Library/Caches/voiceprint/<rec_id>/c<N>.wav`——不放 `/tmp`（重启清空，而用户很可能第二天才回来确认；清空后 UI 就是一堆坏 audio 标签）。

## D8. 原型三级存储（ml 的版本化 + 我 L1 + pm 的"只重建该人"）

```
~/.voiceprint/db/
  emb/<source_id>.npy        # L1：单个来源的窗向量矩阵 (n,192)
  emb/<source_id>.json       #   sidecar：source_id, rec_id, cluster, name, one_off,
                             #             win_ts:[...], created_at, proto_version_in
  protos/<version>/          # L2：人级合并矩阵 <name>.npy
  protos/<version>/manifest.json   # {version, created_at, members:{name:[source_id]},
                                   #  model_mtime, win, hop, scorer}
  protos/CURRENT             # 单行文本，内容是 version（tmp+rename 原子切换）
```
- 回灌：写 `emb/<source_id>.npy`（**直接复制 score 阶段的 `work/<rid>/q_<cluster>.npy`，零推理**）→ 生成新 version 目录（只重算被改的人，其余从上一版硬链接/复制）→ `CURRENT` 原子切换 → 老 version 保留 3 份供回滚。
- **回灌预期 <1s**，pm 的"只重建该人"和 ml 的"可回滚"都满足。
- shadow 模式 `[后置]`：新 version 生成后不立即 promote，先对最近 K 条 `awaiting_review` 重打分，人看差异再切。

# 决议记录 v3（补充：契约与语义，覆盖 §1 的通知/接口部分）

## D10. 「稿子始终存在，确认只是盖个章」——状态机补一条旁路

pm 要「点完立即重写 md」，ux 要「没确认也必须出稿」。这两条合起来意味着 **`awaiting_review` 不能是一道闸门**，否则用户出差一周，那一周的录音全都没有稿。

改法：`render` 完成即写 md（此时自动判定以斜体呈现），同时把录音放进待确认队列。**用户确认只是重渲染一遍、把斜体变粗体**，不产生新事实。

```
... → score → render ──> ready（md 已存在，可读）──用户处置──> confirmed
                     └──> 同时进入 awaiting_review 队列（列表用，不阻塞出稿）
```
因此 `POST /finalize` **不要求所有簇都已处置**，只做三件事：写一条 `finalize` 事件、重渲染、把 status 置 `confirmed`。

## D11. decisions.jsonl 的重放语义（必须按 seq 而非 ts）

ux 问的「assign → revoke → 再 assign 同一个人」这个细节，光靠 ts 排序不够——ts 只有秒级分辨率，同一秒内的 assign 和 revoke 顺序会飘。定死：

```json
{"v":1,"id":"d_0007","seq":7,"type":"assign","audio_hash":"sha256:...",
 "cluster_id":2,"name":"张彤","one_off":false,"spans":[[12.4,133.7]],
 "sim":0.46,"second":0.34,"second_name":"李四","sys_verdict":"ask",
 "scorer":"window","threshold":0.44,"margin":0.05,"proto_version":"p_7f3a",
 "diar_mode":"single","source_id":"src_ab12","ts":"2026-10-28T11:02:11+08:00"}
{"v":1,"id":"d_0008","seq":8,"type":"revoke","revokes":"d_0007","audio_hash":"sha256:...",
 "cluster_id":2,"ts":"2026-10-28T11:02:17+08:00"}
```

- `seq` 单调递增，由写入方在锁内 `max(seq)+1` 分配；**重放只按 `seq` 排序，ts 仅供人读**。
- revoke **必须**带 `revokes: <decision_id>`，指向具体那条 assign。裸 revoke（不指定目标）不接受——否则并发下无法判断撤的是哪次。
- 重放算法（逐 `(audio_hash, cluster_id)`）：
  ```
  cur = None
  for ev in sorted(by seq):
      if ev.type == "assign":                 cur = ev
      elif ev.type == "revoke" and cur and ev.revokes == cur.id:
                                              cur = None      # 不回退到更早的 assign
  # cur is None → 该簇渲染为 未知A/未知B（不是"沿用上一次的名字"）
  ```
  **关键点：revoke 后不回退到更早的 assign。** 这是"最后一次 assign 赢"这种朴素实现会错的地方——用户明确否认过的人不能被一个更早的确认复活。
- 撤销声纹库 = 按 `ev.revokes` 找到那条 assign 的 `source_id`，删 `db/emb/<source_id>.npy*`，重算 L2，**不重建全库**。

## D12. 数字白名单：接口层置 null，不只靠 UI 自觉

ux 要求 `sim` / `second` / `second_name` 三个字段。给，但**在序列化层做白名单**，双保险：

```python
def to_api(ev: ClusterEvidence) -> dict:
    expose = ("low_margin" in (ev.reason or [])) or ev.tier in ("有点像", "无")
    return {
        "top1": ev.top1,
        "sim":         round(ev.s1, 2) if expose else None,
        "second":      round(ev.s2, 2) if expose else None,
        "second_name": ev.second_name if expose else None,
    }
```
`ClusterEvidence` 里加 `second_name: str | None`（原先只有 top1）。除上述两个分支外一律 null，UI 拿不到数字就不可能误渲染成百分数。

## D13. 15 秒跨段拼接样本（不是单段连续 15 秒）

规则：**能量最高的 3 个段 × 5 秒**，按时间顺序拼，段间插 0.25s 静音。
- 段级 RMS 在 score 阶段顺手算（音频已在内存），存进 evidence 的 `seg_rms`，**切音频时不再读第二遍**。
- 每个选中段内取 5 秒最高 RMS 窗口（段本身不足 5 秒则整段取）。
- 总时长 < 4s 或有效段（≥1.5s）< 2 → `concat_url: null` + `reason: ["too_short"]`。
- 落 `~/Library/Caches/voiceprint/<rec_id>/c<N>_<audio_hash8>.wav`，文件名带 hash：重跑后浏览器不会拿旧缓存。
- 用 `soundfile` 定点读，不用 ffmpeg（仓库依赖里没有，为切音频引入不值得）。

`GET /recordings/{rid}` 完整契约见下（ux 需要的 6 个缺口已补）：
